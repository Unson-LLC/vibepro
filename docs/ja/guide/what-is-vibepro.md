# VibeProとは

VibeProは、何を変えるべきかを調べて判断する段階と、その理由を実装・PRレビューまで届ける段階を支えます。ユーザーの課題、判断の根拠、合意した振る舞い、実装参照、確認結果をつなぎます。

AIコーディングエージェントは、技術的には正しいコードを書きながら、そもそも違う問題を解くことがあります。VibeProは、リポジトリローカルの少数の記録で、このプロダクト意図とのずれを確認しやすくします。

```text
依頼・期待する成果
  -> 必要に応じて、問いを立てる ⇄ 調査する ⇄ 証拠で判断し直す
  -> 人間・リポジトリの権限に沿って方針を採択する
  -> Story（課題と受け入れ基準）
    -> Spec（振る舞い、不変条件、実装・テスト参照）
      -> 実装
        -> 検証とレビューの記録
          -> PR要約
```

これは考え方のつながりであり、必須のコマンド順序ではありません。既存Storyから調査を始めることもできます。調査結果からStoryやSpecが自動で確定するわけではありません。

## 各記録の役割

- **調査と判断** は、目的と範囲から問いを立て、取得した根拠と選択肢、未解決事項を残します。ホストAIと `judgment investigate` が調査・再判断を進め、`judgment prepare --investigation` で入力ドラフトへ引き継げます。これは候補の引き継ぎであり、自動採択ではありません。[シニアエンジニア判断](/ja/guide/senior-engineering-judgment)で流れを説明します。

- **Story** は、誰のどんな課題を解決するのかと、変更を受け入れる基準を示します。
- **Spec** は、その課題を具体的な振る舞いと不変条件に変換し、実装と検証へ向かう `code_refs` と `test_refs` を持ちます。
- **検証** は、リポジトリ状態に対して実行・記録したチェックを残します。これはチェックの証拠であり、プロダクトの正しさを約束するものではありません。
- **レビュー** は、人間またはレビュアー役割が何を確認し、どんな結果になったかを記録します。
- **PR準備** は、Story、Spec、検証、レビュー、trace、判断の情報を、機械可読な要約とPR本文へ投影します。

記録はリポジトリの近くに置きます。後からレビューする人が、AIとの非公開な会話や、記録されていない引き継ぎに頼らず、変更の理由をたどれるようにするためです。

## 現行コアでできること

現在のBetaでは、次の操作ができます。

- リポジトリローカルの `.vibepro/` 作業領域を初期化し、出力言語を選ぶ
- Storyを追加・選択・診断する
- ホストAI向けの調査要求を作り、明示された既存Graphify成果物やソースを読み、証拠を加えて判断を見直す
- 下書きまたは確定版のSpecを記録し、構造上の参照を確認する
- 必要な変更について、トレースと明示的な判断を宣言・確認する
- unit、integration、end-to-end、typecheck、buildの検証を実行・記録する
- 軽量なレビューを準備・記録する
- 通常のプルリクエスト運用に渡すPR要約・PR本文を準備する

コマンド契約の正本は、インストールしたCLIの `vibepro help` 出力です。具体的な順序は[導入と最初の実行](/ja/guide/getting-started)を参照してください。

Specは、変更を形にしている間は下書きで進められます。確定版のSpecには、Graphifyコンテキスト、Storyの診断、現在の `HEAD` に対する準備状況の記録という追加の前提があります。確認の順序は[ひとつの変更からPR準備まで](/ja/guide/control-loop)を参照してください。

## 自動で確認することと、確認しないこと

VibeProは、宣言したファイル・シンボル・テスト参照が存在するか、参照に期待したアンカーがあるか、記録した検証コマンドがどんな結果を返したか、といった構造上の事実を確認できます。これにより、証跡を読みやすくします。

意味の解釈や問い・選択肢の生成はホストAIも担います。CLIはモデル向けの `model_request` を返して応答を検証しますが、モデル呼び出し、Graphify生成、外部コネクタでの取得を自律的には行いません。新しい証拠を取得したら古い推薦をそのまま採用せず、再解釈を要求します。取得不足は `unknown` / `partial` / `unavailable` として残します。

これも意味の正しさを保証しません。Graphifyの辺は構造上の候補であり、契約や実行成功の証明ではありません。コード参照が別の振る舞いを指していることも、テストが別のシナリオだけを通過していることもあります。人間によるプロダクト・エンジニアリングレビューと採択の責任は残ります。

同じ理由で、VibeProはアプリケーションコードを実装せず、安全性を認定せず、PRを承認せず、コードをマージしません。これらの権限は、リポジトリのルール、CI、人間に残ります。

## コストと使いどころ

StoryとSpecは、更新して保つための明示的なコストです。プロダクトの課題とコード変更のつながりに価値がある変更で使い、意図した振る舞いが変わったら更新します。README、Issue、設計資料、通常のコードレビューを補完するものであり、それらを一つの自動生成成果物に置き換えるものではありません。

従来の広範なGate DAG、実行コントローラー、レビューのライフサイクル管理、開発効率の予算管理、監査資料の自動生成は廃止しました。現在の判断DAGは、調査・再判断を支える任意の助言です。廃止されたゲートとは異なり、意図の逸脱を自動で認定せず、採択・実行・マージ権限を持ちません。

## 正本と履歴

公開マニュアルは現在のBetaを説明しますが、[バージョン履歴](/ja/reference/version-history)には過去のリリースが登場します。コマンドの正本はインストールした `vibepro help` の出力、バージョンの正本は `package.json` としてください。
