# 専門判断ノードの試作

専門判断ノードは、根拠を添えた観測から、問題の捉え方・因果仮説・選択肢・次に確かめることを生成します。初期版では、開発者の過去の判断から整理した3つの判断則候補を実行できます。

| ノード | 観測すること | 提案する判断 |
| --- | --- | --- |
| `structural-simplification` | 局所修正の反復、複雑性の増加、成果の改善、緊急対応の必要性 | 追加修正と、削除・統合・再設計を比較する。緊急時は被害の封じ込めを優先する |
| `runtime-reachability` | 能力の主張、実装の存在、意図した実行経路の観測 | 「実装がある」と「利用場面で効いている」を区別し、欠けた経路を調べる |
| `evidence-decision-value` | 確認の反復、重大な未確認事項、次の確認が判断を変える可能性 | 判断に必要な確認を選ぶ。解消済みなら追加確認を終えて次の作業へ進む |

それぞれに因果仮説、予測、反証条件があります。たとえば構造の見直しでは、「共通構造を温存した局所修正が、例外と保守負担を累積させている」という仮説から、追加修正に加えて統合・削除を比較候補に出します。成果が改善している場合は、この条件だけで構造の見直しを推しません。

## 実行する

```sh
node bin/vibepro.js judgment suggest --input examples/expert-judgment/structural-simplification.json --json
```

インストール済みのCLIでは `vibepro judgment suggest --input <観測.json> --json` を使います。ワークスペース初期化やStory登録は不要です。結果は標準出力のJSONに返ります。`--json` を省略すると日本語の要約を返します。

例は架空の変更履歴です。実際の案件ではコード、差分、実行ログなどを読んで観測を作ります。

```json
{
  "schema_version": "0.1.0",
  "case_id": "example-repeated-retries",
  "observations": [
    { "id": "fixes", "kind": "repeated_local_fixes", "value": true, "source_refs": ["review:retry-history"] },
    { "id": "complexity", "kind": "complexity_growing", "value": true, "source_refs": ["diff:retry-exceptions"] },
    { "id": "outcome", "kind": "outcome_improving", "value": false, "source_refs": ["report:retry-failures"] },
    { "id": "urgency", "kind": "urgent_containment", "value": false, "source_refs": ["incident:no-active-impact"] }
  ]
}
```

観測の分類は呼び出し元の人またはAIが担当します。たとえば「複雑性が増えた」はコード量だけでは決めず、依存、例外、修正の波及範囲などを案件に合わせて比較します。ノードは文字列のキーワードからこれらの事実を推測しません。

`value` は `true` / `false` です。未確認の観測は省略します。根拠の参照がない観測も未確認として扱います。ノードが `source_refs` の参照先を取得して真偽や鮮度を検証するわけではありません。

## 結果の読み方

- `proposed`: 条件に基づく提案。採用済みという意味ではありません。
- `insufficient`: 判断に必要な観測が足りないか、観測が矛盾しています。`unknowns` と `next_checks` に未解決事項と確認事項を返します。
- `not_applicable`: 観測された条件では、このノードの提案は適用されません。案件全体の安全性や正しさを保証するものではありません。

各結果の根拠、因果仮説、選択肢、反証条件を読んで、次の調査や設計に使います。出力は `advisory: true` / `blocking: false` です。既存の `judgment prepare` / `input adopt` / `evaluate` への自動投入、承認、マージ制御は行いません。既存の判断入力を作る場合は、提案を確認したうえでそのスキーマに整理します。

一部の観測だけで提案または非適用を判断できる場合も、残りの未確認事項は `unknowns` に残します。`next_checks` はその判断に必要な確認を示します。追加確認を終える提案では、新しい判断材料が出た場合の再開条件を返します。

## 過去ログからの抽出と限界

今回の3ノードは、過去ログの本人の発言を人手で照合して作りました。本人の明示した考えと、そこから一般化した因果仮説・分岐・反例を分けています。一般化した部分はすべて `candidate` です。本人がこの条件分岐を確定したことや、未見案件で成果が改善したことを意味しません。

公開可能なルールには匿名の `provenance_ref` を付け、原文・時刻・ログ位置・抽出メッセージのハッシュとの対応は本人用の別ファイルに保存します。個人ログの原文や絶対パスをパッケージへ埋め込みません。

この版はログの自動巡回、自由文の意味抽出、判断則の自動学習を実装していません。テストは条件分岐、反例、未確認の保持、CLI実行を確かめます。専門判断の有用性は、別案件で提案を使ったときに判断や成果がどう変わったかを今後確かめる対象です。
